# TIRI V1 簡易雙語 CMS 規劃草案

> 給後續實作人員（包含 Claude Code）的專案上下文與最小方案草案。  
> 建置日期：2026-08-10  
> 目標上線日：2026-09-15  
> 狀態：**CMS 功能範圍尚未完成內部決策，不得據此直接進入實作。**  
> 目前客戶已提出「新增次層服務項目」的可能需求，需先確認是否包含新增選單、新內頁與動態內容。

## 1. 草案定位

本案採用已確認的 **V1「專業編輯版」** 作為正式新網站版型。本文原先以「只能編輯現有內容」為最小 CMS 方案進行技術規劃，但該範圍尚未獲得明確內部決策。

最小方案的暫定定位是：

> **版型與區塊結構固定，管理者只能修改系統預先定義的內容欄位。**

在 CMS 是否可新增次層、新頁面與動態內容完成決策前，實作者只能進行現況盤點，不得開始建立 CMS 資料模型、管理頁面或前台套用邏輯。

## 2. 專案現況

### 2.1 前台

- V1 位於 `v1/`，目前為靜態 HTML/CSS/JavaScript 網站。
- V1 包含少數重新設計的核心頁面，以及大量套入 V1 外殼的歷史內頁。
- 歷史頁面產生說明位於 `_archive/scripts/v1build/README.md`。但根據 `Files/CMS階段0盤點.md` 的現況驗證，目前 `v1/html/` 已有許多超出產生器的手工演進，重跑產生器會使現站回退。本期應先凍結產生器，不得重跑。
- `v1/html/index.html` 是特例，不完全由核心頁面產生器管理。
- V1 導覽列、社群連結與語言切換的目前唯一來源是 `v1/js/navbar.js`；`shared/navbar.js` 目前主要供 V2，不再與 V1 強制同步。

### 2.2 後台

- 後台位於 `server/`，使用 Flask。
- 現有功能包含管理員登入、帳號設定、表單收件匣、郵件設定及 CSV 匯出。
- 資料庫為公司 SQL Server；開發庫與正式庫由 `.env` 的 `DB_NAME` 區分。
- `server/app.py` 已有資料庫建表、查詢、登入權限與後台樣板架構，CMS 應沿用，不另建新後台或引入另一套 CMS 產品。
- 正式站可由 Flask 依 `FRONTEND_DIR` 與 `FRONTEND_HOSTS` 提供靜態前台。修改前台回應邏輯時，必須保留現有 Host 分流與後台/API 的安全邊界。

## 3. 本期目標

1. 將 V1 整理為正式上線版本。
2. 於現有後台新增「網站內容」管理功能。
3. 指定核心頁面可分別維護中文與英文內容。
4. 可修改既有區塊中指定的文字、圖片、連結、日期、附件、影音網址及聯絡資訊。
5. 修改內容後不得改變 V1 版型、區塊數量、區塊順序與響應式佈局。
6. 保留大量歷史頁面為靜態內容，不進行全站資料重建。
7. 不影響現有六類表單收件、寄信與後台收件匣功能。

## 4. 功能範圍

### 4.1 最小方案暫定管理頁面

若最終選擇「只編輯現有內容」的最小方案，暫定只管理以下核心內容：

| CMS 頁面名稱 | 中文基準頁 | 說明 |
|---|---|---|
| 全站共用資料 | 導覽／頁尾 | 指定導覽文字、頁尾聯絡資料與社群連結 |
| 首頁 | `v1/html/index.html` | 既有主視覺與固定數量的首頁內容區塊 |
| 關於 TIRI | `v1/html/about.html` | 既有標題、內文、圖片、名單與連結 |
| 活動課程 | `v1/html/events.html` | 既有固定卡片與課程資訊，不做無限新增 |
| 知識資源 | `v1/html/knowledge.html` | 既有固定內容卡片 |
| 最新消息 | `v1/html/news.html` | 既有固定消息欄位，不做完整文章發布系統 |
| 會員服務 | `v1/html/membership.html` | 既有會員方案與說明內容 |
| 合作夥伴 | `v1/html/partners.html` | 既有合作夥伴內容與連結 |
| 加入會員 | `v1/html/join.html` | 既有文案與聯絡／表單前台內容；不改表單欄位與處理邏輯 |
| 聯絡我們 | `v1/html/contact.html` | 既有文案、聯絡資訊與連結；不改表單欄位與處理邏輯 |

上表僅是最小方案的技術草案，不是已核定範圍。`login.html`、`search.html`、理監事完整名冊、歷史新聞、歷史活動、年刊、證券雙月刊與其他轉入 V1 外殼的舊頁是否納入，需等 CMS 範圍完成決策。

> 重要：實作前先建立「頁面→區塊→欄位」manifest，並以上表為上限。不要因為系統能力可重複使用，就自動將其他歷史頁面 CMS 化。

### 4.2 可編輯的內容類型

後台可根據欄位定義提供以下輸入：

- 單行文字：標題、副標題、名稱、職稱、按鈕文字、分類。
- 多行文字：內文、摘要、圖片說明、聯絡說明。
- 日期：消息、活動或課程日期。
- 圖片：基本上傳與更換，包含圖片替代文字。
- 連結：站內頁面、外部網址、Email、電話或附件下載連結。
- 附件：基本檔案上傳，主要用於 PDF 與常見 Office 文件。
- 影音網址：YouTube 等既有影音區塊使用的 URL。
- 聯絡資料：地址、電話、Email 及社群連結。
- 顯示狀態：只對 manifest 明確列出的既有項目提供顯示／隱藏。

所有欄位都必須為程式預先白名單化定義，不提供任意欄位、任意 HTML、CSS 或 JavaScript 輸入。

### 4.3 不納入本期範圍

- 拖拉式頁面編輯器。
- 自由排版或修改 V1 視覺樣式。
- 自由新增、刪除或重排內容區塊。
- 自由新增頁面或頁面模板。
- 完整新聞、文章、課程或活動 CRUD 發布系統。
- 任意增減卡片數量或自由拖拉排序。
- 富文字 HTML 編輯器或原始碼編輯器。
- 圖片庫、圖片裁切工具、進階圖片編輯與影片上傳。
- 草稿、排程發布、多層簽核、版本差異與回復。
- 多角色與細部權限系統。
- 自動翻譯、英文翻譯或英文校對。
- 全站歷史頁面 CMS 化或全面英文化。
- 會員登入與其他會員服務。此功能預計於網站上線後再處理，不得與本期 CMS 捆綁實作。
- 變更現有表單欄位、收件流程、寄信邏輯或資料匯出結構。

## 5. 雙語規則

1. 支援語系固定為 `zh-Hant` 與 `en`。
2. 中英文使用相同版型、相同區塊結構與相同欄位 schema。
3. 後台以「中文｜English」頁籤切換，兩種語言的內容分開儲存。
4. 文字、圖片、連結、附件與圖片替代文字皆可按語系分別儲存。圖片若兩種語言共用，仅需設定相同檔案路徑。
5. 系統不自動翻譯，也不自行產生英文內容。英文內容由 TIRI 提供。
6. 不得將缺少的英文文案自動用中文覆蓋。尚未提供英文的頁面，應保留現有英文預設內容，或在頁面對應確認前不開放語言切換。
7. 實作前必須盤點現有英文頁面與 URL，產出一份中英文頁面對應表。優先保留現有公開 URL，不自行發明新的 URL 規則或全站重導。
8. 語言切換必須前往當前頁面的對應語言頁，不得無條件一律跳回首頁。

## 6. 管理後台 UX

### 6.1 導覽與頁面

- 於現有後台側邊列增加「網站內容」項目。
- 進入後先選擇頁面，再切換「中文｜English」。
- 欄位按前台區塊分組，欄位標籤使用非技術用語，例如「首頁主視覺／主標題」，不直接顯示 `hero.title` 等程式 key。
- 圖片欄位需顯示目前圖片預覽，連結與附件欄位需顯示目前值。
- 多行內文使用純文字 textarea。本期不提供 TinyMCE 或任意 HTML 編輯。
- 提供單一「儲存」動作，儲存後直接成為前台內容。不做草稿、排程或審核狀態。
- 儲存成功或失敗應沿用現有後台 toast／對話框樣式，不重建一套 UI kit。

### 6.2 權限

- 沿用現有管理員 session 與 `require_auth`。
- 本期不新增角色與權限層級。
- 所有寫入、上傳與刪除檔案動作必須要求登入，並使用 POST。
- 不可從前端送入任意資料表名稱、欄位名稱或檔案路徑。

## 7. 建議資料模型

為了維持簡單並避免每增加一個欄位就修改 SQL schema，建議以「每頁每語系一份 JSON」儲存：

```sql
CREATE TABLE cms_pages (
    page_slug NVARCHAR(100) NOT NULL,
    locale NVARCHAR(10) NOT NULL,
    content_json NVARCHAR(MAX) NOT NULL,
    updated_at NVARCHAR(19) NULL,
    updated_by INT NULL,
    CONSTRAINT PK_cms_pages PRIMARY KEY (page_slug, locale)
);
```

說明：

- `page_slug`：例如 `global`、`home`、`about`、`events`。
- `locale`：僅允許 `zh-Hant` 或 `en`。
- `content_json`：僅儲存 manifest 允許的 key/value。
- `updated_by`：對應現有 `users.id`；本期只作基本紀錄，不做完整版本歷程。
- 建表必須使用與現有 `init_db()` 一致的 idempotent 方式，不得破壞現有四張表與資料。

欄位 schema 不由後台使用者建立，而是寫在程式版本控制中，例如 `server/cms_schema.py`：

```python
CMS_PAGES = {
    "home": {
        "label": "首頁",
        "sections": [
            {
                "label": "主視覺",
                "fields": [
                    {"key": "hero.title", "label": "主標題", "type": "text", "max_length": 80},
                    {"key": "hero.summary", "label": "說明文字", "type": "textarea", "max_length": 300},
                    {"key": "hero.image", "label": "背景圖片", "type": "image"},
                    {"key": "hero.cta_label", "label": "按鈕文字", "type": "text", "max_length": 30},
                    {"key": "hero.cta_url", "label": "按鈕連結", "type": "url"},
                ],
            },
        ],
    },
}
```

實際名稱與檔案可調整，但必須保持「固定 schema＋JSON 值＋嚴格驗證」的邊界。

## 8. 前台套用策略

### 8.1 必要原則

- V1 靜態 HTML 內的已確認內容應保留為 fallback。
- SQL Server 無資料、欄位缺少或 CMS 查詢異常時，前台應顯示 V1 原始內容，不能顯示空白區塊。
- 不得將管理者內容以未清理的 `innerHTML` 直接注入前台。
- 文字應以轉義後的純文字套入；URL、圖片與附件路徑需分類驗證。
- 只對 manifest 列出的節點與屬性進行替換。

### 8.2 建議實作

優先使用服務器端套入，避免前台載入後才替換文字的閃動與 SEO 基準內容過期：

1. 在可編輯的 V1 節點上加入穩定的 `data-cms-*` 標記，不改變視覺。
2. 以目前 `v1/html/` 作為本期事實源加入標記；不重跑已過時的 V1 產生器。
3. Flask 在前台 Host 收到本期管理頁面請求時，讀取對應靜態 HTML，再將資料庫內已驗證的值套入指定節點。
4. 未列入 CMS 的歷史頁面仍使用原本 `send_from_directory` 流程。
5. 可對處理後的 HTML 做短時間 cache，但後台儲存後必須清除對應頁面與語系的 cache。

若經現況驗證後，服務器端套入會大幅破壞現有 Host 分流，才改用一支小型前台內容腳本與 JSON API。如改用客戶端方案，仍必須保留靜態 fallback、白名單定義、輸入驗證與無 HTML 注入原則，並在實作說明中記錄這個取捨。

## 9. 圖片與附件

### 9.1 儲存

- 上傳檔案不得放在每次部署可能被覆蓋的程式資料夾。
- 以 `.env` 的 `CMS_UPLOAD_DIR` 指定持久化路徑，開發與正式環境分開。
- 資料庫僅存相對路徑與必要顯示資訊，不將大型檔案存入 SQL Server。
- 正式上線前必須確認檔案資料夾會與 SQL Server 資料一起備份。

### 9.2 安全與限制

- 圖片預設允許 JPG、PNG 與 WebP；不允許 SVG 與可執行檔。
- 附件僅允許實際需要的 PDF 與指定 Office 格式。
- 檔案類型應同時驗證副檔名與上傳內容，不信任瀏覽器傳入的 MIME type。
- 單檔預設上限 10 MB；若實際歷史文件超過此限制，先盤點後再調整，不預設開放無限大小。
- 檔名使用 UUID 或其他不可預測的安全名稱，不直接使用用戶上傳的原始檔名作為磁碟路徑。
- 取用檔案的 route 必須阻擋 path traversal，且前台 Host 只開放公開內容檔案，不得暴露 `.env`、資料庫設定或任意伺服器檔案。

## 10. 輸入驗證

- 所有頁面、語系與 field key 必須存在於程式 manifest。
- 文字欄位依版型設定合理字數上限，並在後台顯示說明。
- URL 根據欄位類型只允許安全的 `https://`、站內相對路徑、`mailto:` 或 `tel:`，拒絕 `javascript:` 等協定。
- 圖片與附件僅能指向允許的站內路徑或經確認的外部資源。
- 儲存時依 manifest 重建一份干淨 JSON，不原樣儲存 request 的任意 key。
- 多行文字保留換行，但輸出時一律進行 HTML escape。

## 11. 實作階段

### 階段 0：前置盤點（不先寫功能）

1. 確認 V1 正式基準版本與目前 Git 狀態。
2. 盤點本期九個核心頁面與全站共用資料的實際來源檔，並以 `Files/CMS階段0盤點.md` 的現況驗證為基準。
3. 產出中英文頁面與 URL 對應表。
4. 產出欄位 manifest：頁面、區塊、field key、類型、字數限制、預設值與對應 DOM 節點。
5. 確認英文尚缺內容清單，不自行翻譯。

階段 0 交付物應為一份可檢查的欄位清單，後續實作不得超出清單。

### 階段 1：資料層與後台基礎

1. 新增 idempotent `cms_pages` 建表邏輯。
2. 新增 CMS schema/manifest 程式設定。
3. 新增讀取、驗證、儲存與 fallback 服務層。
4. 後台新增「網站內容」頁面、頁面選擇與語系頁籤。
5. 先以「首頁主視覺」作為縱向切片，驗證後台→SQL Server→前台完整流程後再擴充其他頁面。

### 階段 2：圖片、附件與核心頁面

1. 實作圖片／附件上傳、驗證與持久化路徑。
2. 依 manifest 分批套用核心頁面。
3. 在 `_archive/scripts/v1build/README.md` 明確標記產生器已凍結，避免後續誤重跑造成現站回退。
4. 建立或整理中英文導覽與頁面對應，僅限本期已列頁面。

### 階段 3：內容套用與測試

1. 以已確認 V1 中文內容建立初始值。
2. 套入 TIRI 提供的英文內容；缺件保留在清單中，不自行補文。
3. 測試每一種欄位、語系分離、fallback、圖片與附件。
4. 測試所有核心頁面的桌機與手機版型。
5. 回歸測試現有表單、後台收件匣、郵件設定與帳號登入。
6. 執行 `npm run check`，並修復由本次變更造成的站內連結問題。

### 階段 4：上線

1. 確認正式 SQL Server 與 `CMS_UPLOAD_DIR` 備份方式。
2. 部署後以正式 Host 測試中英文頁面與上傳檔案。
3. 使用後台修改一組測試內容，確認前台正確顯示並可復原。
4. 清除測試內容，完成正式上線。

## 13. 驗收條件

### 13.1 後台

- 已登入管理員可進入「網站內容」。
- 可選擇本期頁面並切換中文／English。
- 可修改 manifest 列出的文字、日期、圖片、連結、附件與影音網址。
- 不在 manifest 的 key 無法透過 request 寫入資料庫。
- 儲存後重新整理頁面、重新登入或重新啟動伺服器，資料仍存在。
- 中文與英文資料不會互相覆蓋。

### 13.2 前台

- 指定頁面顯示 CMS 儲存內容，版型結構與 V1 一致。
- CMS 記錄缺少或資料庫查詢失敗時，顯示 V1 靜態 fallback，不出現空白頁面。
- 文字、URL 與上傳檔案不能造成任意 HTML／JavaScript 執行。
- 中英文切換前往正確對應頁面。
- 編輯日常合理長度的內容後，桌機與手機版型無明顯破版。
- 未納入 CMS 的歷史頁面、圖片、文件與內部連結可正常開啟。

### 13.3 回歸

- 六類現有前台表單可正常送出。
- 後台收件匣、垃圾桶、郵件設定、帳號設定與 CSV 匯出正常。
- 開發庫 `TIRI_dev` 與正式庫 `TIRI` 維持分離。
- `npm run check` 無本次變更造成的新增失敗。

## 14. 給實作者的操作規則

1. **先盤點、後實作。** 不要看到「CMS」就直接建通用 CRUD。
2. **不得擴充範圍。** 本期僅做本文列出的核心頁面與欄位。
3. **凍結過時產生器。** 本期以目前 `v1/html/` 為事實源，不重跑 `_archive/scripts/v1build/`；若未來要恢復產生器，應另立同步專案。
4. **保留 fallback。** 資料庫沒有內容時仍要顯示已確認 V1 文案。
5. **不信任使用者輸入。** 文字、URL、檔案與 JSON key 都要有白名單與驗證。
6. **不影響表單系統。** CMS 修改不得改寫現有收件、寄信與 Host 分流流程。
7. **英文缺件要列表，不要補寫。**
8. **每一階段都要可驗證。** 先完成一個頁面的縱向切片，通過後再擴展到全部核心頁面。
9. **不要提前實作會員功能。** 會員登入與會員服務是上線後的另一階段。
